\section{Εισαγωγή}
\subsection{Περιγραφή και Κίνητρο της Εργασίας}
Στην εποχή της ψηφιακής εκπαίδευσης, η πληθώρα των διαθέσιμων διαδικτυακών μαθημάτων έχει δημιουργήσει ένα τεράστιο τοπίο πληροφόρησης. Οι εκπαιδευόμενοι συχνά καλούνται να αναζητήσουν εκπαιδευτικό υλικό σε πολλαπλές, ετερογενείς πλατφόρμες (π.χ. Coursera, Udemy, EdX), γεγονός που καθιστά τη διαδικασία εύρεσης του κατάλληλου μαθήματος χρονοβόρα και δύσκολη.

Η παρούσα εργασία πραγματεύεται τη σχεδίαση και υλοποίηση του \textbf{ Course Aggregator}, ενός «οριζόντιου αποθετηρίου» (horizontal repository). Το σύστημα αυτό δεν φιλοξενεί το ίδιο το εκπαιδευτικό περιεχόμενο (βίντεο, σημειώσεις), αλλά λειτουργεί ως ένας ενδιάμεσος κόμβος που συγκεντρώνει (harvests) μεταδεδομένα από πολλαπλές εξωτερικές πηγές. Στόχος είναι η παροχή μίας ενιαίας διεπαφής αναζήτησης και η προσφορά προστιθέμενης αξίας μέσω προηγμένων υπηρεσιών Μηχανικής Μάθησης (Machine Learning).

\subsection{Στόχοι και Αντικείμενο}
Ο βασικός σκοπός του έργου είναι η ανάπτυξη ενός ολοκληρωμένου πληροφοριακού συστήματος που συνδυάζει σύγχρονες τεχνολογίες διαδικτύου και επεξεργασίας μεγάλων δεδομένων. Οι επιμέρους στόχοι αναλύονται ως εξής:

\begin{enumerate}
    \item \textbf{Συγκέντρωση και Ομογενοποίηση Δεδομένων (Data Aggregation):} 
    Η δημιουργία μηχανισμών (connectors) για την άντληση δεδομένων από ετερογενή εξωτερικά API και ο μετασχηματισμός τους σε ένα ενιαίο σχήμα βάσης δεδομένων.
    \item \textbf{Ενιαία Διεπαφή Χρήστη (Unified Frontend):} 
    Η ανάπτυξη μιας σύγχρονης διαδικτυακής εφαρμογής (SPA) με χρήση της βιβλιοθήκης React. Η διεπαφή επιτρέπει στον χρήστη την αναζήτηση μαθημάτων με λέξεις-κλειδιά, την εφαρμογή σύνθετων φίλτρων (γλώσσα, επίπεδο, πάροχος) και την προβολή αναλυτικών πληροφοριών.    
    \item \textbf{Ευφυής Επεξεργασία Δεδομένων (Big Data \& ML):} 
    Η αξιοποίηση του πλαισίου Apache Spark για την εκτέλεση εργασιών μεγάλης κλίμακας. Συγκεκριμένα, υλοποιούνται αλγόριθμοι για:
    \begin{itemize}
        \item \textbf{Συστάσεις Μαθημάτων (Recommendations):} Εύρεση παρόμοιων μαθημάτων βάσει περιεχομένου (Content-Based Filtering) με χρήση τεχνικών NLP (TF-IDF, Cosine Similarity).
        \item \textbf{Ομαδοποίηση (Clustering):} Αυτόματη κατηγοριοποίηση μαθημάτων σε θεματικές ενότητες με χρήση αλγορίθμων όπως ο LDA (Latent Dirichlet Allocation).
        \item \textbf{Προσωποποίηση (Personalization):} Παραγωγή προτάσεων βάσει του ιστορικού και των προτιμήσεων του χρήστη (Collaborative Filtering/ALS).
    \end{itemize}
\end{enumerate}

Το Frontend αναπτύχθηκε με τη χρήση της βιβλιοθήκης \textbf{React.js} και του εργαλείου \textbf{Vite}, προσφέροντας μια σύγχρονη, γρήγορη και αποκριτική διεπαφή χρήστη (Responsive UI). Η εφαρμογή υλοποιεί σύνθετες λειτουργίες όπως δυναμική αναζήτηση και φιλτράρισμα σε πραγματικό χρόνο, σύστημα ταυτοποίησης χρηστών με JWT, προσωποποιημένο πίνακα ελέγχου (Dashboard) και οπτικοποίηση αποτελεσμάτων Μηχανικής Μάθησης (Machine Learning). Ιδιαίτερη έμφαση δόθηκε στη διαχωρισμένη αρχιτεκτονική (Decoupled Architecture), όπου το Frontend επικοινωνεί με το Backend μέσω REST API, εξασφαλίζοντας επεκτασιμότητα και συντηρησιμότητα.

\subsection{Εισαγωγή}

\subsubsection{Σκοπός του Έργου} 
Στόχος της εργασίας είναι η υλοποίηση ενός οριζόντιου συστήματος αναζήτησης μαθημάτων, το οποίο λειτουργεί ως ενδιάμεσος κόμβος μεταξύ των παρόχων εκπαίδευσης (π.χ. Ο ρόλος του Frontend είναι κρίσιμος, καθώς καλείται να παρουσιάσει με φιλικό τρόπο τα αποτελέσματα σύνθετων αλγορίθμων που εκτελούνται στο παρασκήνιο (Clustering, Recommendations) και να προσφέρει εργαλεία διαχείρισης για τους διαχειριστές του συστήματος.

\subsubsection{Ανάλυση Απαιτήσεων Frontend}
Βάσει των προδιαγραφών σχεδιασμού, το υποσύστημα διεπαφής χρήστη καλύπτει τις εξής λειτουργικές απαιτήσεις:
\begin{enumerate}
    \item \textbf{Αναζήτηση και Φιλτράρισμα:} Δυνατότητα αναζήτησης με λέξεις-κλειδιά και εφαρμογή φίλτρων (γλώσσα, επίπεδο, πηγή, θεματική).
    \item \textbf{Προβολή Λεπτομερειών:} Εμφάνιση αναλυτικών πληροφοριών μαθήματος και παραπομπή στην αρχική πηγή.
    \item \textbf{Συστήματα Συστάσεων:} Οπτική απεικόνιση των αποτελεσμάτων του Spark ML ("Similar Courses") στη σελίδα λεπτομερειών.
    \item \textbf{Διαχείριση Χρηστών:} Υλοποίηση μηχανισμού εγγραφής (Sign Up) και σύνδεσης (Login) με διαχείριση συνεδρίας (Session).
    \item \textbf{Admin Dashboard:} Ειδική σελίδα για την εκκίνηση διαδικασιών συγχρονισμού (Harvesting) και εκπαίδευσης μοντέλων ML.
    \item \textbf{Analytics:} Γραφική απεικόνιση στατιστικών στοιχείων χρήσης και κατανομής μαθημάτων.
\end{enumerate}

    \item \textbf{Βελτιστοποιημένο Build:} Χρησιμοποιεί το Rollup για την παραγωγή του τελικού κώδικα (production build).

\subsubsection{Κεντρική Δρομολόγηση και Ασφάλεια}
Η διαχείριση της πλοήγησης γίνεται στο αρχείο \texttt{App.jsx}. Εδώ ορίζονται οι διαδρομές και εφαρμόζεται η λογική προστασίας μέσω του Component \texttt{ProtectedRoute}.

Το \texttt{ProtectedRoute} λειτουργεί ως Wrapper. Ελέγχει την ύπαρξη του JWT token στο LocalStorage και το ρόλο του χρήστη (User vs Admin). Αν ο χρήστης δεν έχει δικαίωμα πρόσβασης, ανακατευθύνεται αυτόματα.

\begin{minted}[label=src/App.jsx,
frame=lines,
framesep=2mm,
baselinestretch=1.2,
fontsize=\footnotesize,
breaklines,
linenos
]{javascript}
import { BrowserRouter as Router, Routes, Route, Navigate } from 'react-router-dom';

// Component προστασίας διαδρομών
const ProtectedRoute = ({ children, isAdminRequired }) => {
    // Ανάκτηση δεδομένων χρήστη από Local Storage
    const userString = localStorage.getItem('user');
    
    // Έλεγχος Αυθεντικοποίησης: Αν δεν υπάρχει χρήστης, ανακατεύθυνση στο Login
    if (!userString) {
        console.log("Access Denied: No user found");
        return <Navigate to="/login" replace />;
    }
    
    const user = JSON.parse(userString);

    // Έλεγχος Εξουσιοδότησης: Αν απαιτείται ρόλος Admin και ο χρήστης δεν είναι
    if (isAdminRequired && user.role?.toLowerCase() !== 'admin') {
        console.log("Access Denied: Admin role required");
        return <Navigate to="/" replace />;
    }

    // Αν όλα είναι εντάξει, επιστροφή του παιδιού-component
    return children;
};

function App() {
  return (
    <Router>
      <div className="App">
        <Navbar />
        <Routes>
          {/* Public Routes - Προσβάσιμες από όλους */}
          <Route path="/" element={<Home />} />
          <Route path="/login" element={<Login />} />
          <Route path="/signup" element={<SignUp />} />
          <Route path="/courses/:id" element={<CourseDetails />} />

          {/* Protected Admin Route - Προσβάσιμη μόνο από Admin */}
          <Route 
            path="/admin-dashboard" 
            element={
              <ProtectedRoute isAdminRequired={true}>
                <AdminDashboard />
              </ProtectedRoute>
            } 
          />
          
          {/* Catch-all για 404 - Χειρισμός άγνωστων URL */}
          <Route path="*" element={<Error />} />
        </Routes>
      </div>
    </Router>
  );
}
\end{minted}

Αυτό σημαίνει ότι οι λίστες επαναϋπολογίζονται μόνο όταν αλλάξουν τα δεδομένα των μαθημάτων και όχι σε κάθε ανανέωση της οθόνης.

\begin{minted}[label=src/pages/Home.jsx (Optimization), frame=lines, framesep=2mm, baselinestretch=1.2, fontsize=\footnotesize, breaklines, linenos]{javascript}
// Υπολογισμός μοναδικών γλωσσών μόνο όταν αλλάξει το allCourses
const uniqueLanguages = useMemo(() => 
  [...new Set(allCourses.map(c => c.language).filter(Boolean))], 
[allCourses]);

const uniqueLevels = useMemo(() => 
  [...new Set(allCourses.map(c => c.level).filter(Boolean))], 
[allCourses]);

const uniqueCategories = useMemo(() => 
  [...new Set(allCourses.map(c => c.category).filter(Boolean))], 
[allCourses]);
\end{minted}

Για την εφαρμογή των φίλτρων κατά την πληκτρολόγηση ή την επιλογή από τα dropdowns, χρησιμοποιείται το hook \texttt{useEffect}. Κάθε αλλαγή στα κριτήρια αναζήτησης (\texttt{searchTerm}) ή στα φίλτρα (\texttt{filters}) πυροδοτεί εκ νέου τον υπολογισμό της λίστας προς εμφάνιση (\texttt{result}).

\begin{minted}[label=src/pages/Home.jsx,
frame=lines,
framesep=2mm,
baselinestretch=1.2,
fontsize=\footnotesize,
breaklines,
linenos
]{javascript}
useEffect(() => {
  if (allCourses.length === 0) return;

  let result = [...allCourses];

  // 1. Φιλτράρισμα βάσει κειμένου (Search Bar) - Case Insensitive
  if (searchTerm) {
    const term = searchTerm.toLowerCase();
    result = result.filter(course => 
      (course.title || "").toLowerCase().includes(term) ||
      (course.description || "").toLowerCase().includes(term)
    );
  }

  // 2. Εφαρμογή δυναμικών φίλτρων (Dropdowns)
  if (filters.language) {
    result = result.filter(c => 
        c.language && c.language.toLowerCase() === filters.language.toLowerCase()
    );
  }
  if (filters.level) {
    result = result.filter(c => c.level === filters.level);
  }
  if (filters.category) {
    result = result.filter(c => c.category === filters.category);
  }

  // Ενημέρωση state με τα αποτελέσματα και επαναφορά σελίδας στο 1
  setCourses(result);
  setCurrentPage(1);
}, [searchTerm, filters, allCourses]); // Dependencies: Τρέχει όταν αλλάξει κάποιο από αυτά
\end{minted}

\subsection{Στρατηγική Διαχείρισης Κατάστασης (State Management)}

Για τη διαχείριση της κατάστασης της εφαρμογής (Application State), επιλέχθηκε μια αποκεντρωμένη προσέγγιση αντί της χρήσης μιας καθολικής βιβλιοθήκης όπως το Redux. Η απόφαση αυτή βασίστηκε στην πολυπλοκότητα της εφαρμογής και στην ανάγκη για γρήγορη ανάπτυξη. Συγκεκριμένα:

\begin{itemize}
    \item \textbf{Local State:} Χρησιμοποιείται το \texttt{useState} για δεδομένα που αφορούν αποκλειστικά ένα Component (π.χ. τιμή πεδίου αναζήτησης, άνοιγμα/κλείσιμο modal).
    \item \textbf{Persisted State:} Για την αυθεντικοποίηση (JWT token, user info) και τις προτιμήσεις του διαχειριστή (Activity Logs), χρησιμοποιείται το \texttt{localStorage}. Αυτό εξασφαλίζει ότι η κατάσταση διατηρείται ακόμα και μετά από ανανέωση της σελίδας (page refresh).
    \item \textbf{Server State:} Τα δεδομένα των μαθημάτων και των στατιστικών θεωρούνται "Server State" και ανανεώνονται μέσω του \texttt{useEffect} κατά την πλοήγηση, εξασφαλίζοντας ότι ο χρήστης βλέπει πάντα φρέσκα δεδομένα χωρίς την ανάγκη περίπλοκου caching στον client.
\end{itemize}

\subsection{Διαχείριση Σφαλμάτων και Ανθεκτικότητα}

Το Frontend έχει σχεδιαστεί ώστε να διαχειρίζεται αποτυχίες του συστήματος χωρίς να "καταρρέει" (crash) η εφαρμογή:

\begin{itemize}
    \item \textbf{API Failures:} Σε περίπτωση που το Backend δεν ανταποκρίνεται (π.χ. Network Error 500), η εφαρμογή εμφανίζει διακριτικά μηνύματα σφάλματος (Toast Notifications ή Error Banners) ενημερώνοντας τον χρήστη να δοκιμάσει αργότερα.
    \item \textbf{Broken Links/Routes:} Υλοποιήθηκε μια ειδική σελίδα "404 Not Found" (Catch-all route), ώστε αν ο χρήστης πληκτρολογήσει λάθος URL, να μπορεί να επιστρέψει εύκολα στην αρχική σελίδα.
    \item \textbf{Session Expiration:} Οι HTTP Interceptors ελέγχουν τις απαντήσεις του server. Αν ανιχνευθεί σφάλμα 401 (Unauthorized), το σύστημα αντιλαμβάνεται ότι το token έληξε, αποσυνδέει αυτόματα τον χρήστη και τον ανακατευθύνει στη σελίδα εισόδου.
\end{itemize}

\subsection{Αρχιτεκτονική και Δομή}

Η εφαρμογή ακολουθεί την αρχιτεκτονική MVC, η οποία διαχωρίζει τη λογική σε τέσσερα βασικά επίπεδα:

\begin{itemize}
    \item \textbf{Models (Μοντέλα)}: Ορίζουν τη δομή των δεδομένων μέσω Mongoose schemas. Κάθε model αντιπροσωπεύει μια συλλογή (collection) στη MongoDB και περιλαμβάνει validation rules, default values και relationships μεταξύ των entities.
    
    \item \textbf{Controllers (Ελεγκτές)}: Περιέχουν την επιχειρησιακή λογική της εφαρμογής. Κάθε controller είναι υπεύθυνος για τη διαχείριση των HTTP requests, την επικοινωνία με τη βάση δεδομένων, την επεξεργασία των δεδομένων και την επιστροφή των κατάλληλων responses.
    
    \item \textbf{Routes (Διαδρομές)}: Ορίζουν τα API endpoints και τη δρομολόγηση των αιτημάτων στους αντίστοιχους controllers. Κάθε route file ομαδοποιεί λογικά συναφή endpoints (π.χ. \texttt{/courses}, \texttt{/users}, \texttt{/analytics}).
    
    \item \textbf{Middleware (Ενδιάμεσο Λογισμικό)}: Παρέχει διασταυρούμενες λειτουργίες που εκτελούνται πριν ή μετά τους controllers, όπως authentication, authorization, logging, error handling και CORS configuration.
\end{itemize}

Αυτός ο διαχωρισμός επιτρέπει την εύκολη επέκταση του συστήματος, τη δοκιμή μεμονωμένων components και την ανεξάρτητη ανάπτυξη διαφορετικών τμημάτων της εφαρμογής.

\textbf{Ανάλυση Πεδίων:}

\begin{itemize}
    \item \texttt{externalId}: Το μοναδικό αναγνωριστικό του μαθήματος στην εξωτερική πηγή.     \item \texttt{language}, \texttt{level}, \texttt{category}: Μεταδεδομένα για φιλτράρισμα και κατηγοριοποίηση. Έχουν προεπιλεγμένες τιμές για την αντιμετώπιση ελλιπών δεδομένων από τις εξωτερικές πηγές.
    
    \item \texttt{keywords}: Array από λέξεις-κλειδιά που εξάγονται από το URL ή παρέχονται από την πηγή. Χρησιμοποιούνται για βελτίωση της αναζήτησης.
    
    \item \texttt{source}, \texttt{provider}: Αναγνωρίζουν την προέλευση του μαθήματος. Ο \texttt{provider} είναι η επίσημη ονομασία (π.χ. "Coursera"), ενώ ο \texttt{source} μπορεί να είναι το όνομα του connector.
    
    \item \texttt{url}: Το πλήρες URL για πρόσβαση στο μάθημα στην αρχική πλατφόρμα.
    
    \item \texttt{cluster\_id}, \texttt{cluster\_label}: Προστέθηκαν για την υποστήριξη των αλγορίθμων clustering που εκτελούνται στο Spark layer. Το \texttt{cluster\_id} είναι ο αριθμητικός αναγνωριστής του cluster, ενώ το \texttt{cluster\_label} περιέχει την ανθρώπινα αναγνώσιμη ετικέτα (π.χ. "Machine Learning", "Web Development"). Αρχικά έχουν την τιμή -1 και κενό string αντίστοιχα, μέχρι να εκτελεστεί το clustering job.
    
    \item \texttt{timestamps}: Το option αυτό προσθέτει αυτόματα τα πεδία \texttt{createdAt} και \texttt{updatedAt}, χρήσιμα για tracking και debugging.
\end{itemize}

\textbf{Βασικά Χαρακτηριστικά του Schema:}

\begin{itemize}
    \item \textbf{Βασικά Στοιχεία Χρήστη}: Τα πεδία \texttt{firstName}, \texttt{lastName} και \texttt{email} είναι υποχρεωτικά. Το \texttt{email} είναι unique και χρησιμεύει ως username για την είσοδο στο σύστημα.
    
    \item \textbf{Password Security}: Το password αποθηκεύεται σε hashed μορφή με χρήση bcrypt (salt rounds: 10). Δεν αποθηκεύεται ποτέ σε plaintext.
    
    \item \textbf{Role-Based Access Control}: Το πεδίο \texttt{role} καθορίζει τα δικαιώματα του χρήστη. Υπάρχουν δύο ρόλοι:
    \begin{itemize}
        \item \texttt{'user'}: Κανονικός χρήστης με πρόσβαση σε βασικές λειτουργίες (αναζήτηση, αγαπημένα, προβολή μαθημάτων).
        \item \texttt{'admin'}: Διαχειριστής με πρόσβαση σε διαχειριστικές λειτουργίες (συγχρονισμός δεδομένων, εκτέλεση Spark jobs, διαχείριση χρηστών).
    \end{itemize}
    
    \item \textbf{Favorite Courses}: Το πεδίο \texttt{favoriteCourses} είναι ένα array από ObjectIds που αναφέρονται στη συλλογή Course. Χρησιμοποιείται Mongoose \texttt{populate()} για να ανακτηθούν τα πλήρη course objects όταν χρειάζεται.
    
    \item \textbf{Recently Viewed}: Το πεδίο \texttt{recentlyViewed} αποθηκεύει τα τελευταία 30 μαθήματα που προέβαλε ο χρήστης. Κάθε entry περιέχει:
    \begin{itemize}
        \item \texttt{courseId}: Reference στο μάθημα
        \item \texttt{viewedAt}: Timestamp της προβολής
    \end{itemize}
    Το array διατηρείται ταξινομημένο με τα πιο πρόσφατα πρώτα και περιορίζεται στα 30 items για αποδοτικότητα.
    
    \item \textbf{Permission Level}: Το πεδίο \texttt{permissionLevel} (default: 1) επιτρέπει μελλοντική επέκταση με περισσότερους ρόλους και granular permissions.
\end{itemize}

\subsubsection{Recommendation Schema}

Το μοντέλο Recommendation αποθηκεύει τα αποτελέσματα των αλγορίθμων συστάσεων που εκτελούνται στο Spark layer. Κάθε εγγραφή αναπαριστά μια σύσταση: δηλαδή ότι το μάθημα Β συνιστάται για όποιον ενδιαφέρεται για το μάθημα Α.

\begin{minted}[
frame=lines,
framesep=2mm,
baselinestretch=1.2,
fontsize=\footnotesize,
breaklines,
linenos
]{javascript}
const RecommendationSchema = new mongoose.Schema({
    source_course_id: { 
        type: String, 
        required: true, 
        index: true 
    },
    recommended_course_id: { 
        type: String, 
        required: true 
    },
    score: Number,
    rank: Number
}, { 
    collection: 'course_recommendations' 
});
\end{minted}

\textbf{Δομή και Λειτουργία:}

\begin{itemize}
    \item \textbf{Source Course}: Το πεδίο \texttt{source\_course\_id} είναι το μάθημα για το οποίο γίνεται η σύσταση. Έχει index για γρήγορη αναζήτηση όλων των συστάσεων για ένα συγκεκριμένο μάθημα.
    
    \item \textbf{Recommended Course}: Το πεδίο \texttt{recommended\_course\_id} είναι το μάθημα που συνιστάται.
    
    \item \textbf{Similarity Score}: Το πεδίο \texttt{score} περιέχει το σκορ ομοιότητας (συνήθως από 0 έως 1), υπολογισμένο από τον αλγόριθμο του Spark (cosine similarity, Jaccard distance κ.λπ.). Όσο μεγαλύτερο το score, τόσο πιο παρόμοια είναι τα μαθήματα.
    
    \item \textbf{Rank}: Το πεδίο \texttt{rank} υποδεικνύει τη σειρά κατάταξης της σύστασης (1 = καλύτερη σύσταση, 2 = δεύτερη καλύτερη κ.ο.κ.). Το Spark layer κρατάει μόνο τις top-5 συστάσεις για κάθε μάθημα.
    
    \item \textbf{Collection Name}: Το option \texttt{collection: 'course\_recommendations'} εξασφαλίζει ότι το Mongoose θα χρησιμοποιήσει το συγκεκριμένο όνομα collection στη MongoDB, αντί του default pluralized name.
\end{itemize}

\textbf{Παράδειγμα Χρήσης:}
Αν το μάθημα "Introduction to Python" έχει \texttt{\_id: "abc123"}, μια εγγραφή στο Recommendation collection μπορεί να είναι:
\begin{verbatim}
{
  source_course_id: "abc123",
  recommended_course_id: "def456",
  score: 0.87,
  rank: 1
}
\end{verbatim}
Αυτό σημαίνει ότι το μάθημα με id "def456" (π.χ. "Data Structures in Python") είναι η πρώτη σύσταση για όποιον κοιτάζει το "Introduction to Python", με similarity score 0.87.

\subsection{Authentication και Authorization}

\subsubsection{JWT-Based Authentication}

Το σύστημα χρησιμοποιεί \textbf{JSON Web Tokens (JWT)} για την ταυτοποίηση των χρηστών. Τα JWT είναι ένα ανοιχτό πρότυπο (RFC 7519) που επιτρέπει την ασφαλή μεταφορά πληροφοριών μεταξύ δύο μερών ως ένα JSON object. Τα tokens είναι digitally signed και περιέχουν claims (δηλώσεις) σχετικά με τον χρήστη.

\textbf{Ροή Λειτουργίας:}
\begin{enumerate}
    \item Ο χρήστης συνδέεται με email/password
    \item Το backend επαληθεύει τα credentials και δημιουργεί ένα JWT
    \item Το JWT αποθηκεύεται στη MongoDB (collection \texttt{Token}) και στέλνεται στον client
    \item Ο client στέλνει το JWT σε κάθε επόμενο request (μέσω cookie ή Authorization header)
    \item Το middleware \texttt{verifyToken} ελέγχει την εγκυρότητα του token πριν επιτρέψει την πρόσβαση
\end{enumerate}

\begin{minted}[
frame=lines,
framesep=2mm,
baselinestretch=1.2,
fontsize=\footnotesize,
breaklines,
linenos
]{javascript}
const verifyToken = async (req, res, next) => {
    let token = req.cookies.token;
    const authHeader = req.headers['authorization'];
    
    if (!token && authHeader && 
        authHeader.startsWith('Bearer ')) {
        token = authHeader.split(' ')[1];
    }
    
    if (!token) {
        return res.status(401).json({ 
            message: "Access Denied: No Token Provided" 
        });
    }
    
    try {
        const tokenExists = await Token.findOne({ token });
        if (!tokenExists) {
            return res.status(401).json({ 
                message: "Token is no longer valid" 
            });
        }
        
        const verified = jwt.verify(
            token, 
            process.env.JWT_SECRET
        );
        
        req.userID = verified.id;
        req.userRole = verified.role;
        next();
    } catch (error) {
        res.status(401).json({ 
            message: "Token expired or invalid" 
        });
    }
};
\end{minted}

\textbf{Λεπτομερής Ανάλυση του Middleware:}

\begin{enumerate}
    \item \textbf{Εξαγωγή Token}: Το middleware υποστηρίζει δύο τρόπους αποστολής του token:
    \begin{itemize}
        \item \textbf{HTTP-only Cookie}: Πιο ασφαλής για web browsers, καθώς το token δεν είναι προσβάσιμο από JavaScript του client, προστατεύοντας από XSS attacks.
        \item \textbf{Authorization Header}: Για mobile apps, API clients και testing tools που δεν υποστηρίζουν cookies. Το format είναι: \texttt{Authorization: Bearer <token>}.
    \end{itemize}
    
    \item \textbf{Token Blacklisting}: Πριν την επαλήθευση, ελέγχεται αν το token υπάρχει στο \texttt{Token} collection της MongoDB. Αυτό υλοποιεί έναν μηχανισμό blacklisting:
    \begin{itemize}
        \item Κατά την αποσύνδεση (signout), το token διαγράφεται από το collection.
        \item Έτσι, ακόμα και αν ένας εισβολέας αποκτήσει πρόσβαση σε ένα token, μετά την αποσύνδεση το token γίνεται άκυρο.
    \end{itemize}
    
    \item \textbf{JWT Verification}: Χρησιμοποιείται η βιβλιοθήκη \texttt{jsonwebtoken} για την επαλήθευση του signature και την αποκωδικοποίηση του payload. Το \texttt{JWT\_SECRET} από το environment χρησιμεύει ως το κλειδί υπογραφής.
    
    \item \textbf{Request Enrichment}: Μετά την επιτυχή επαλήθευση, το middleware προσθέτει τα \texttt{req.userID} και \texttt{req.userRole} στο request object, τα οποία χρησιμοποιούνται από τους controllers για personalization και authorization.
    
    \item \textbf{Error Handling}: Διαφορετικά error messages για διαφορετικά σενάρια (missing token, invalid token, expired token) βοηθούν στο debugging και την καλύτερη εμπειρία χρήστη.
\end{enumerate}

\subsubsection{Σύστημα Συστάσεων}

Η συνάρτηση \texttt{getSimilarCourses()} ανακτά συναφή μαθήματα:

\begin{minted}[
frame=lines,
framesep=2mm,
baselinestretch=1.2,
fontsize=\footnotesize,
breaklines,
linenos
]{javascript}
const getSimilarCourses = async (req, res) => {
    try {
        const { id } = req.params;

        const recommendations = await Recommendation.find({
            $or: [
                { source_course_id: id },
                { recommended_course_id: id }
            ]
        })
        .sort({ rank: 1 })
        .limit(5)
        .lean();
        
        if (!recommendations.length) return res.json([]);

        const recommendedCourseIds = recommendations.map(r => 
            r.recommended_course_id === id 
                ? r.source_course_id 
                : r.recommended_course_id
        );
        
        const courses = await Course.find({ 
            _id: { $in: recommendedCourseIds } 
        }).lean();

        const results = recommendations.map(rec => {
            const targetId = rec.recommended_course_id === id 
                ? rec.source_course_id 
                : rec.recommended_course_id;
            const courseData = courses.find(
                c => c._id.toString() === targetId
            );
            return courseData 
                ? { ...courseData, score: rec.score } 
                : null;
        }).filter(Boolean);

        res.json(results);
    } catch (error) {
        res.status(500).json({ 
            error: 'Internal Server Error' 
        });
    }
};
\end{minted}

\textbf{Τεχνική Υλοποίηση:}
\begin{itemize}
    \item Χρήση \texttt{\$or} operator για συμμετρική αναζήτηση (το μάθημα μπορεί να είναι source ή recommended).
    \item Δύο ξεχωριστά queries: ένα για τις συστάσεις και ένα για τα course objects.
    \item Join των αποτελεσμάτων σε application level για προσθήκη του similarity score.
\end{itemize}

const runSparkJob = async (req, res) => {
    const scriptPath = "../spark-layer/jobs/recommender.py";
    const recommender_option = req.params.option || '0';

    const pythonProcess = spawn(
        'python3', 
        [scriptPath, recommender_option], 
        { shell: true }
    );

    let output = "";
    let errorOutput = "";

    pythonProcess.stdout.on('data', (data) => {
        output += data.toString();
    });

    pythonProcess.stderr.on('data', (data) => {
        errorOutput += data.toString();
        console.error("Spark Log:", data.toString());

        if (!res.headersSent) {
            res.status(408).json({ 
                message: "Spark Job Timeout" 
            });
        }
    }, 180000); // 3 minute timeout

    pythonProcess.on('close', (code) => {
        clearTimeout(timeout);
        if (code !== 0) {
            if (!res.headersSent) {
                return res.status(500).json({ 
                    message: "Spark Error", 
                    error: errorOutput 
                });
            }
        }
        if (!res.headersSent) {
            res.status(200).json({ 
                message: "Success", 
                details: output 
            });
        }
    });
};
\end{minted}

    \item Error propagation στο frontend για debugging.
\end{itemize}

\section{Harvester (Data Connectors)}

Το σύστημα συλλογής δεδομένων (data harvesting layer) αποτελεί την εισόδου δεδομένων της εφαρμογής. Είναι υπεύθυνο για τη συστηματική και αυτόματη συγκέντρωση εκπαιδευτικού περιεχομένου από διαφορετικές εξωτερικές πηγές (πλατφόρμες online learning), τη μετατροπή τους σε ενιαίο format και την αποθήκευσή τους στη βάση δεδομένων.

Η αρχιτεκτονική των connectors έχει σχεδιαστεί με γνώμονα:
\begin{itemize}
    \item \textbf{Επεκτασιμότητα}: Δυνατότητα προσθήκης νέων πηγών χωρίς αλλαγές στον core κώδικα.
    \item \textbf{Ομοιομορφία}: Κάθε connector ακολουθεί το ίδιο interface, ανεξάρτητα από τη δομή του εξωτερικού API.
    \item \textbf{Αντοχή σε λάθη}: Η αποτυχία ενός connector δεν επηρεάζει τους υπόλοιπους.
    \item \textbf{Διαχείριση Ετερογενών Δεδομένων}: Κάθε πηγή έχει διαφορετική δομή δεδομένων που πρέπει να κανονικοποιηθεί.
\end{itemize}

\subsection{Αρχιτεκτονική Connectors}

Κάθε connector υλοποιείται ως ένα ανεξάρτητο JavaScript module (\texttt{.js} file) που τοποθετείται στο directory \texttt{services/connectors/}. Αυτή η modular προσέγγιση επιτρέπει την εύκολη προσθήκη, τροποποίηση ή αφαίρεση πηγών δεδομένων χωρίς να επηρεάζεται ο υπόλοιπος κώδικας.

\textbf{Κάθε connector εξάγει (exports) δύο υποχρεωτικές συναρτήσεις:}

\begin{enumerate}
    \item \texttt{getCourses()}: 
    \begin{itemize}
        \item \textbf{Ρόλος}: Αναλαμβάνει την επικοινωνία με το εξωτερικό API.
        \item \textbf{Λειτουργία}: Διαχειρίζεται authentication (αν απαιτείται), κάνει τα HTTP requests και επιστρέφει τα ακατέργαστα δεδομένα όπως έρχονται από την πηγή.
        \item \textbf{Επιστροφή}: Ένα JavaScript object ή array με τα raw data από το API.
    \end{itemize}
    
    \item \texttt{normalize(data)}:
    \begin{itemize}
        \item \textbf{Ρόλος}: Μετατρέπει τα ετερογενή δεδομένα σε ενιαίο σχήμα.
        \item \textbf{Λειτουργία}: Παίρνει τα raw data από το \texttt{getCourses()} και τα χαρτογραφεί στα πεδία του Course schema.
        \item \textbf{Επιστροφή}: Ένα array από course objects έτοιμα για αποθήκευση στη MongoDB.
    \end{itemize}
\end{enumerate}

\textbf{Γιατί αυτός ο διαχωρισμός;}

Η αρχιτεκτονική αυτή ακολουθεί την αρχή του \textit{separation of concerns}:
\begin{itemize}
    \item Η λογική επικοινωνίας με το API (authentication, pagination, error handling) είναι ξεχωριστή από τη λογική μετασχηματισμού δεδομένων.
    \item Αν αλλάξει η δομή του εξωτερικού API, χρειάζεται να τροποποιηθεί μόνο η \texttt{normalize()}.

\section{Spark Layer}
\subsection{System Architecture}
Το σύστημα σε pySpark που σχεδιάστηκε και υλοποιήθηκε ακολουθεί την εξής ροή δεδομένων (Pipeline):
\begin{enumerate}
    \item Data Ingestion: Ανάγνωση δεδομένων από το collection courses της MongoDB μέσω Spark
    \item Preprocessing (NLP): Καθαρισμός κειμένου (Title + Description + Keywords με SparkNLP
    \item Vectorization: Μετατροπή κειμένου σε αριθμητικά διανύσματα (TF-IDF)
    \item Modeling:
    \begin{itemize}
        \item Clustering (LDA) για θεματική ομαδοποίηση.
        \item Similarity Calculation (Cosine Similarity / LSH).
    \end{itemize}
    \item Data Export: Εγγραφή των συστάσεων πίσω στη MongoDB (course\_recommendations/courses για τα πεδία cluster\_id και cluster\_label).
\end{enumerate}

\subsection{Μεθοδολογία \& Αλγόριθμοι}

\subsubsection{NLP Pipeline}
Βρίσκεται το \texttt{~jobs/utils/} και αποτελείται από τα εξής βήματα
\begin{enumerate}
    \item \texttt{DocumentAssembler} Ετοιμάζει τα δεδομένα, τα μετατρέπει σε μορφή document, ένα format που μπορεί να διαχειριστεί η βιβλιοθήκη SparkNLP
    \item \texttt{Tokenizer} Σπάει το αρχικό κείμενο στις λέξεις (tokens) από τις οποίες αποτελείται, 
    \item \texttt{Normalizer} Καθαρίζει τα tokens αφαιρώντας σημεία στίξης, σύμβολα και ειδικούς χαρακτήρες με χρήση regex, διατηρώντας συνήθως μόνο τους αλφαριθμητικούς χαρακτήρες ώστε να απομείνουν οι καθαρές λέξεις για περαιτέρω ανάλυση.
    \item \texttt{StopWordsCleaner} Αφαιρεί τα tokens τα οποία δεν έχουν σημασιολογικό περιεχόμενο, κοινές λέξεις όπως τα "and", "or" etc. Μεταξύ αυτών προστέθηκαν και κάποιες έξτρα όπως οι λέξεις "courses, "introduction", "student" etc.
    \item \texttt{LemmatizerModel/Stemmer} Εναλλακτικές τεχνικές για να ανάγουμε μία λέξη στην αρχική της μορφή (ρίζα). Ο Stemmer είναι γρηγορότερος καθώς χρησιμοποιεί προκαθορισμένους κανόνες για την κοπή των καταλήξεων, αλλά μπορεί να καταλήξει σε μη υπαρκτές λέξεις (π.χ. το "studies" να γίνει "studi"). Αντίθετα, το LemmatizerModel χρησιμοποιεί λεξικό και μορφολογική ανάλυση για να βρει το πραγματικό λήμμα της λέξης (π.χ. το "better" να γίνει "good"), προσφέροντας μεγαλύτερη ακρίβεια στη σημασιολογική ανάλυση. Χρησιμοποιείται pretrained εκδοχή του Lemmatizer.
    \item \texttt{Finisher} Αποτελεί το τελευταίο στάδιο του NLP Pipeline, το οποίο μετατρέπει τα δεδομένα από την εσωτερική μορφή "Annotations" της SparkNLP σε απλά Spark SQL Arrays. Αυτό γίνεται ώστε τα αποτελέσματα του Pipeline να είναι συμβατά με τις κλασικές βιβλιοθήκες μηχανικής μάθησης του SparkML (όπως ο CountVectorizer).
\end{enumerate}

\subsubsection{TF-IDF}
Η TF-IDF (Term Frequency–Inverse Document Frequency) είναι μια στατιστική μέθοδος που χρησιμοποιείται σε εφαρμογές ΝLP για την αξιολόγηση της σημασίας μιας λέξης για ένα έγγραφο σε σχέση με μια μεγαλύτερη συλλογή εγγράφων (corpus). 

Το TF‐IDF αποτυπώνει δύο βασικές ιδέες σχετικά με τη συνάφεια ενός όρου με ένα
έγγραφο. Πρώτον, θα περιμέναμε ότι όσο πιο συχνά εμφανίζεται ένας όρος σε ένα έγγραφο, τόσο πιο σημαντικός είναι για το έγγραφο αυτό (TF). Δεύτερον, δεν είναι όλοι οι όροι εξίσου σημαντικοί σε καθολικό επίπεδο. Είναι πιο σημαντικό να συναντήσετε μια λέξη που εμφανίζεται σπάνια σε ολόκληρο το corpus παρά μια λέξη που εμφανίζεται στα περισσότερα έγγραφα έτσι, η μετρική χρησιμοποιεί το αντίστροφο της εμφάνισης της λέξης σε έγγραφα στο πλήρες corpus (IDF).

Η συχνότητα των λέξεων σε ένα σώμα κειμένων τείνει να κατανέμεται εκθετικά. Μία κοινή λέξη εμφανίζεται εκθετικά περισσότερες φορές από μία σπάνια λέξη. Το IDF είναι μία μετρική που δίνει σε αυτές στις σπάνιες λέξεις τεράστιο βάρος σε σχέση με τις συχνές, τις οποίες πρακτικά θα τις αγνοούσε. Αυτό διατυπώνεται ως εξής:

\begin{equation}
    {\displaystyle \mathrm {idf} (t,D)=\log {\frac {N}{n_{t}}}}
\end{equation}

Πρόκειται τεχνική βασισμένη στο bag-of-words model. Δηλαδή έχει το μειονέκτημα ότι δεν δίνει καμία σημασία στη διάταξη των λέξεων, στη δομή της πρότασης ή στις αρνήσεις. Επίσης το μοντέλο αδυνατεί να αντιμετοπίσει το γεγονός ότι η ίδια λέξη μπορεί να έχει πολλές σημασίες ανάλογα σε διαφορετικά contexts. Μία εναλλακτική που θα λάμβανε υπόψη τα παραπάνω θα ήταν η χρήση embeddings, αλλά αυτό ξεπερνάει τα πλαίσια της εργασίας.

To TF υλοποιείται από τον CountVectorizer και το IDF από το την κλάση του ίδιου ονόματος. Χρησιμοποιήθηκαν οι παράμετροι \texttt{minDF} για τον αποκλεισμό πολύ σπάνιων όρων και \texttt{maxDF} για την αφαίρεση όρων που εμφανίζονται σε πάνω από το 60\% των εγγράφων, λειτουργώντας ως δυναμικό stop-word filter.

\begin{minted}[

framesep=2mm,

]{python}
  cv = CountVectorizer(inputCol="tokens", outputCol="raw_features",
    minDF=10, maxDF=0.6, vocabSize=20000)
  cv_model = cv.fit(valid_tokens_df)

\subsubsection{Αναπαράσταση Δεδομένων: Document-Term Matrix}
Το τελικό αποτέλεσμα της διαδικασίας TF-IDF είναι ένα Document-Term Matrix. Σε αυτή τη δομή:
\begin{itemize}
    \item Κάθε \textbf{γραμμή} αντιπροσωπεύει ένα μάθημα.
    \item Κάθε \textbf{στήλη} αντιπροσωπεύει μια μοναδική λέξη από το λεξιλόγιο των 20.000 όρων.
    \item Η τιμή σε κάθε κελί είναι το βάρος TF-IDF που υποδηλώνει τη σημασία της λέξης για το συγκεκριμένο μάθημα.
\end{itemize}

Λόγω της φύσης των κειμένων, η συντριπτική πλειοψηφία των κελιών περιέχει την τιμή μηδέν. Για τη βελτιστοποίηση της μνήμης και της υπολογιστικής ισχύος, το Spark χρησιμοποιεί τη δομή \texttt{SparseVector}. Αντί για έναν πλήρη πίνακα (Dense Matrix), αποθηκεύονται μόνο:
\begin{enumerate}
    \item Το συνολικό μέγεθος του λεξιλογίου.
    \item Οι δείκτες (indices) των στηλών που έχουν μη μηδενική τιμή.
    \item Οι αντίστοιχες τιμές TF-IDF για αυτούς τους δείκτες.
\end{enumerate}
Αυτή η προσέγγιση επιτρέπει στον αλγόριθμο να εκτελεί πράξεις γραμμικής άλγεβρας (όπως ο υπολογισμός cosine similarity) εξαιρετικά γρήγορα, αγνοώντας τα μηδενικά στοιχεία.

\subsection{Στρατηγικές Παραγωγής Συστάσεων (Recommendation Scenarios)}
Στο σύστημα υλοποιήθηκαν (στο \texttt{recommender.py}) τέσσερις διαφορετικές προσεγγίσεις για τον υπολογισμό της ομοιότητας μεταξύ των μαθημάτων, καθεμία με διαφορετικά πλεονεκτήματα ως προς την ακρίβεια και την ταχύτητα. 

\subsubsection{Σενάριο 0: Exact Cosine Similarity (Ground Truth)} Το σενάριο αυτό αποτελεί το "χρυσό πρότυπο" για την αξιολόγηση των συστάσεων. Χρησιμοποιεί cosine similarity, η οποία υπολογίζει τη γωνία μεταξύ δύο διανυσμάτων TF-IDF στον πολυδιάστατο χώρο με τον εξής τύπο:
\begin{equation}
    \text{similarity} = \cos(\theta) = \frac{\mathbf{A} \cdot \mathbf{B}}{|\mathbf{A}| |\mathbf{B}|} 
\end{equation}

\textbf{Τεχνική Υλοποίηση:} 
\begin{itemize} 
    \item Τα διανύσματα κανονικοποιούνται (L2 Normalization) έτσι ώστε το μήκος τους να είναι 1. 
    \item Ο υπολογισμός γίνεται μέσω κατανεμημένου πολλαπλασιασμού πινάκων ($A A^T$) με τη χρήση της κλάσης \texttt{BlockMatrix} του Spark.
    \item \textbf{Πλεονέκτημα:} Μέγιστη μαθηματική ακρίβεια. 
    \item \textbf{Μειονέκτημα:} Υψηλό υπολογιστικό κόστος $O(N^2)$, το οποίο όμως διαχειρίζεται το Spark μέσω παραλληλισμού. 
\end{itemize}

\subsubsection{Σενάριο 1: Approximate k-NN (MinHash LSH)} 
Για περιπτώσεις πολύ μεγάλων δεδομένων, η χρήση προσέγγισης είναι απαραίτητη λόγω του απαγορευτικού $O(N^2)$ της brute-force σύγκρισης (Σενάριο 0). Χρησιμοποιήθηκε ο αλγόριθμος \textbf{LSH} και συγκεκριμένα η υλοποίηση \texttt{MinHashLSH}.

\textbf{Λειτουργία:} Αντί να συγκρίνουμε κάθε μάθημα με όλα τα υπόλοιπα, ο αλγόριθμος υπολογίζει έναν αριθμό από \textit{similarity preserving signatures} για κάθε έγγραφο. Στη συνέχεια, κατανέμει τα μαθήματα με βάση αυτές τις υπογραφές σε κάδους (\textit{buckets}). Μαθήματα που είναι παρόμοια έχουν πολύ μεγάλη πιθανότητα να καταλήξουν στον ίδιο κάδο, περιορίζοντας δραστικά τον αριθμό των συγκρίσεων που πρέπει να γίνουν. 

\begin{itemize} 
    \item \textbf{Γιατί Jaccard Distance:} Ο αλγόριθμος \texttt{MinHash} είναι μαθηματικά σχεδιασμένος να προσεγγίζει τον συντελεστή ομοιότητας \textbf{Jaccard}. Η επιλογή αυτή είναι ιδανική για δεδομένα κειμένου (όπως οι περιγραφές μας), καθώς η ομοιότητα Jaccard μετρά την επικάλυψη των συνόλων των λέξεων μεταξύ δύο εγγράφων ($\frac {|A \cap B|}{|A \cup B|}$), δίνοντας έμφαση στην παρουσία κοινών όρων ανεξάρτητα από το μέγεθος του διανύσματος.
    
    \item \textbf{MinHash vs Bucketed Random Projection (BRP):} Ενώ o \texttt{BucketedRandom-} \texttt{ProjectionLSH} χρησιμοποιείται κυρίως για την προσέγγιση της Ευκλείδειας απόστασης σε dense vectors. Τα διανύσματα TF-IDF είναι \textit{sparse}, το MinHash επικεντρώνεται στα μη-μηδενικά στοιχεία (λέξεις που υπάρχουν), προσφέροντας πολύ ταχύτερα αποτελέσματα για την εύρεση παρόμοιων κειμένων.
    
    \item \textbf{Χρησιμότητα:} Επιτρέπει την εκτέλεση του συστήματος συστάσεων σε πραγματικό χρόνο ή σε περιβάλλοντα με εκατομμύρια εγγραφές, θυσιάζοντας ένα ελάχιστο ποσοστό ακρίβειας για τεράστια κέρδη σε ταχύτητα και πόρους.
\end{itemize}

\textbf{Γιατί η Ομοιότητα Συνημιτόνου αποτελεί το Ground Truth;} Παρόλο που ο αλγόριθμος MinHash LSH χρησιμοποιεί την απόσταση Jaccard για λόγους ταχύτητας, το Cosine Similarity επιλέχθηκε ως το σημείο αναφοράς για τους εξής λόγους:

\begin{enumerate} 
    \item \textbf{Ενσωμάτωση των Βαρών TF-IDF:} Η ομοιότητα Jaccard εξετάζει τα έγγραφα ως σύνολα λέξεων (παρουσία ή απουσία μιας λέξης). Αντίθετα, η Cosine Similarity υπολογίζεται πάνω στα διανύσματα των βαρών TF-IDF. Αυτό σημαίνει ότι λαμβάνει υπόψη τη σχετική σημασία κάθε λέξης. Για παράδειγμα, αν δύο μαθήματα μοιράζονται τη σπάνια λέξη "Kubernetes", η Cosine Similarity θα τους δώσει πολύ υψηλότερο σκορ από ότι αν μοιράζονταν την κοινή λέξη "Introduction", ενώ η Jaccard θα τις αντιμετώπιζε σχεδόν ισότιμα.
    
    \item \textbf{Ανθεκτικότητα στο Μέγεθος του Κειμένου (Length Invariance):} Η Cosine Similarity μετράει τη γωνία των διανυσμάτων και όχι το μέγεθός τους. Αυτό την καθιστά ιδανική για περιγραφές μαθημάτων, καθώς ένα μάθημα με πολύ μεγάλη περιγραφή και ένα με σύντομη περιγραφή μπορούν να θεωρηθούν παρόμοια αν "κοιτάζουν" προς την ίδια νοηματική κατεύθυνση, ανεξάρτητα από το πλήθος των λέξεων.
    
    \item \textbf{Ακρίβεια έναντι Προσέγγισης:} Το Σενάριο 0 (Exact Cosine) εκτελεί τον πλήρη μαθηματικό υπολογισμό για κάθε πιθανό ζεύγος εγγράφων ($O(N^2)$). Σε αντίθεση με το LSH, το οποίο είναι μια προσεγγιστική μέθοδος που μπορεί να "χάσει" κάποια παρόμοια ζεύγη αν δεν καταλήξουν στον ίδιο κάδο, η exact μέθοδος εγγυάται την εύρεση των απολύτως καλύτερων συστάσεων βάσει του μοντέλου TF-IDF.
\end{enumerate}

\subsubsection{Σενάριο 2: Thematic Recommender (LDA + LSH)} 
Αυτή η προσέγγιση μετατοπίζει την εστίαση από τις μεμονωμένες λέξεις στις «λανθάνουσες» (latent) νοηματικές ενότητες. Αντί να συγκρίνουμε μαθήματα βάσει κοινών όρων, τα συγκρίνουμε βάσει των θεμάτων (\textit{topics}) στα οποία ανήκουν.

\textbf{Λειτουργία:} 
\begin{itemize} 
    \item \textbf{Μοντελοποίηση LDA:} Χρησιμοποιείται το μοντέλο \textbf{LDA (Latent Dirichlet Allocation)}, ένας αλγόριθμος \textit{soft clustering}. Το LDA θεωρεί ότι κάθε μάθημα είναι ένα μείγμα διαφόρων θεμάτων και κάθε θέμα ένα μείγμα διαφόρων λέξεων. Το αποτέλεσμα για κάθε μάθημα είναι ένα διάνυσμα πιθανοτήτων (π.χ. 70\% Προγραμματισμός, 20\% Βάσεις Δεδομένων, 10\% Δίκτυα). Αν και ιδανικό για documents μεγαλύτερης έκτασης όπως research papers και άρθρα, η χρήση του προσφέρει και εδώ κάποια πλεονεκτήματα.

    \item \textbf{Διανύσματα Θεμάτων (Topic Distributions):} Σε αντίθεση με τα διανύσματα TF-IDF που είναι εξαιρετικά αραιά (\textit{sparse}), οι κατανομές θεμάτων του LDA είναι πυκνά διανύσματα (\textit{dense}) μικρής διάστασης (ίσης με τον αριθμό των θεμάτων $k$). Δύο μαθήματα θεωρούνται παρόμοια αν οι κατανομές των θεμάτων τους «μοιάζουν» στατιστικά.

    \item \textbf{Χρήση BRP LSH:} Λόγω της πυκνής φύσης αυτών των διανυσμάτων, ο υπολογισμός της ομοιότητας μπορεί να γίνει αποδοτικά με τον αλγόριθμο \textbf{Bucketed Random Projection (BRP) LSH}. Ο BRP χρησιμοποιεί τυχαίες προβολές για να ομαδοποιήσει τα διανύσματα σε κάδους βάσει της Ευκλείδειας απόστασης ή cosine distance, καθιστώντας την αναζήτηση θεματικά παρόμοιων μαθημάτων εξαιρετικά γρήγορη.

    \item \textbf{Πλεονέκτημα (Εννοιολογική Συνάφεια):} Το κύριο πλεονέκτημα αυτής της μεθόδου είναι η αντιμετώπιση του προβλήματος της συνωνυμίας. Δύο μαθήματα μπορεί να αναφέρονται στο ίδιο αντικείμενο χρησιμοποιώντας εντελώς διαφορετικό λεξιλόγιο (π.χ. το ένα να αναφέρει «ανάπτυξη εφαρμογών» και το άλλο «software engineering»). Το LDA είναι σε θέση να αναγνωρίσει ότι και τα δύο ανήκουν στο ίδιο θέμα, καθώς η στατιστική συνύπαρξη των υπολοίπων λέξεων στο κείμενο (context) προσδιορίζει την κοινή θεματική ενότητα, προσφέροντας συστάσεις που ξεπερνούν τους περιορισμούς των απλών στατιστικών μεθόδων NLP.
\end{itemize}

\subsubsection{Σενάριο 3: Υβριδικό Μοντέλο Συστάσεων (Hybrid Recommender)} 
Το υβριδικό μοντέλο αποτελεί την πιο ολοκληρωμένη προσέγγιση του συστήματος, καθώς επιχειρεί να συνδυάσει τα πλεονεκτήματα της λεξιλογικής ομοιότητας (TF-IDF) και της θεματικής συνάφειας (LDA), εξαλείφοντας παράλληλα τις αδυναμίες τους.

\textbf{Λειτουργία και Υλοποίηση:} 
\begin{itemize} 
    \item \textbf{Συνδυασμός Αποτελεσμάτων (Outer Join):} Το σύστημα εκτελεί μια πράξη \textit{Outer Join} μεταξύ των αποτελεσμάτων των δύο προηγούμενων μοντέλων. Με αυτόν τον τρόπο, διασφαλίζεται ότι μια σύσταση θα ληφθεί υπόψη ακόμα και αν εντοπίστηκε μόνο από το ένα εκ των δύο μοντέλων.

    \item \textbf{Σταθμισμένος Μέσος Όρος (Weighted Scoring):} Για κάθε ζεύγος μαθημάτων, υπολογίζεται μια τελική «υβριδική απόσταση» χρησιμοποιώντας συντελεστές βαρύτητας (\textit{weights}). Στην παρούσα υλοποίηση χρησιμοποιήθηκε η αναλογία 60\% για το TF-IDF και 40\% για το LDA:
    \begin{equation}
        D_{hybrid} = (w_{tfidf} \cdot Dist_{tfidf}) + (w_{lda} \cdot Dist_{lda})
    \end{equation}
    
    \item \textbf{Διαχείριση Ελλιπών Δεδομένων (Penalization):} Σε περιπτώσεις όπου ένα ζεύγος μαθημάτων προτείνεται από το ένα μοντέλο αλλά όχι από το άλλο, το σύστημα εφαρμόζει μια «ποινή» (\textit{penalty}), αποδίδοντας τη μέγιστη δυνατή απόσταση (1.0) στο μοντέλο που δεν εντόπισε τη συνάφεια. Αυτό διασφαλίζει ότι οι πιο ισχυρές συστάσεις είναι αυτές που αναγνωρίζονται και από τις δύο μεθόδους.

    \textbf{Πλεονεκτήματα:} Η υβριδική προσέγγιση επιτρέπει στο σύστημα να προτείνει μαθήματα που έχουν τόσο παρόμοιους τίτλους και περιγραφές (μέσω TF-IDF), όσο και παρόμοιο εννοιολογικό υπόβαθρο (μέσω LDA), προσφέροντας μια πιο «φυσική» και ανθρώπινη εμπειρία χρήστη.
\end{itemize}

\subsubsection{Τελική Επιλογή και Κατάταξη} 
Ανεξάρτητα από τη μέθοδο υπολογισμού που ακολουθείται (Exact, LSH, LDA ή Hybrid), το τελευταίο στάδιο του αγωγού επεξεργασίας είναι κοινό για όλα τα σενάρια. Σκοπός είναι ο περιορισμός του όγκου των δεδομένων και η διατήρηση μόνο των πιο συναφών προτάσεων για τον τελικό χρήστη.

\textbf{Διαδικασία:} 
\begin{itemize} 
    \item \textbf{Χρήση Window Functions:} Για την αποτελεσματική διαχείριση των δεδομένων σε περιβάλλον Spark, χρησιμοποιούνται οι συναρτήσεις παραθύρου (\textit{Window Functions}). Αυτό επιτρέπει στο σύστημα να ομαδοποιεί τις συστάσεις ανά μάθημα-πηγή (\texttt{id\_a}) και να τις ταξινομεί εσωτερικά. 
    
    \item \textbf{Φιλτράρισμα Top-5:} Εφαρμόζεται η συνάρτηση \texttt{row\_number()} για την απόδοση μιας σειράς κατάταξης σε κάθε πρόταση βάσει του score ομοιότητας (ή της απόστασης). Στη συνέχεια, το σύστημα φιλτράρει και κρατά μόνο τις 5 επικρατέστερες συστάσεις (\texttt{$rank <= 5$}). \end{itemize}

\begin{minted}[frame=lines, fontsize=\footnotesize]{python}
window_spec = Window.partitionBy("id_a").orderBy(fun.col("distance").asc())

lsh_knn_results = flattened_lsh \
  .withColumn("rank", fun.row_number().over(window_spec)) \
  .filter(fun.col("rank") <= 5)
\end{minted}

\subsection{Θεματική Συσταδοποίηση (Topic-based Clustering)} 
Αντί για την παραδοσιακή συσταδοποίηση (όπως ο K-Means), το σύστημα χρησιμοποιεί το μοντέλο LDA (Latent Dirichlet Allocation) για την οργάνωση των μαθημάτων. Η προσέγγιση αυτή είναι πιο εξελιγμένη καθώς αντιμετωπίζει τα μαθήματα ως μείγματα θεμάτων και όχι ως στατικά αντικείμενα που ανήκουν αυστηρά σε μία ομάδα.

\textbf{Λειτουργία και Υλοποίηση:} 
\begin{itemize} 
    \item \textbf{Soft vs Hard Clustering:} Σε αντίθεση με παραδοσιακούς αλγορίθμους όπως ο K-Means, οι οποίοι εκτελούν «σκληρή» συσταδοποίηση (\textit{hard clustering}) αναθέτοντας κάθε μάθημα αποκλειστικά σε μία ομάδα, το LDA υιοθετεί μια πιθανοτική προσέγγιση. Θεωρεί ότι κάθε μάθημα αποτελεί ένα \textbf{μείγμα (mixture)} διαφορετικών θεμάτων. Για παράδειγμα, ένα μάθημα "Machine Learning in Finance" μπορεί να αναλυθεί από το LDA ως 60\% "Data Science" και 40\% "Finance", αντί να εξαναγκαστεί σε μία μόνο από τις δύο κατηγορίες.

    \item \textbf{Εξαγωγή Κύριας Συστάδας (Maximum Likelihood):} Παρόλο που το μοντέλο παράγει μια κατανομή πιθανοτήτων, για τις ανάγκες της οργάνωσης της βάσης δεδομένων, το σύστημα απομονώνει το θέμα με την υψηλότερη πιθανότητα (\textit{argmax}). Αυτό το επικρατέστερο θέμα χρησιμοποιείται ως η «κύρια συστάδα» (\texttt{cluster\_label}), επιτρέποντας την κατηγοριοποίηση των μαθημάτων χωρίς να χάνεται η εσωτερική πληροφορία της θεματικής συνάφειας που χρησιμοποιείται στο Σενάριο 2.

    \item \textbf{Ερμηνευσιμότητα και Εξαγωγή Θεματικών Τίτλων:} Ένα καθοριστικό πλεονέκτημα του LDA έναντι του K-Means είναι η δυνατότητα απόδοσης νοήματος στις συστάδες. Ενώ ο K-Means παράγει ανώνυμες ομάδες (π.χ. «Cluster 1», «Cluster 2»), καθιστώντας δύσκολη την κατανόηση του περιεχομένου τους χωρίς περαιτέρω ανάλυση, το LDA παρέχει για κάθε θέμα μια λίστα με τις επικρατέστερες λέξεις (\textit{top words}). 

    Για παράδειγμα, αν ένα θέμα περιλαμβάνει τις λέξεις "algorithm", "data", "structure", ο προγραμματιστής ή ο τελικός χρήστης μπορεί άμεσα να αντιληφθεί ότι η συστάδα αφορά την Πληροφορική. Αυτή η δυνατότητα επέτρεψε στο σύστημα να "τιτλοφορεί" εμμέσως τις κατηγορίες, προσφέροντας μια πολύ πιο διαφανή και φιλική προς τον χρήστη εμπειρία.
    
    \item \textbf{Υλοποίηση στο Spark:} Η διαδικασία υλοποιείται μέσω του \texttt{pyspark.ml.clu-} \texttt{stering.LDA}. Τα αποτελέσματα μετασχηματίζονται ώστε να εξαχθεί ο δείκτης (index) του επικρατέστερου θέματος. 
\end{itemize}

\textbf{Η Σημασία του Clustering στις Συστάσεις:} 
Η πληροφορία της συστάδας δεν χρησιμοποιείται μόνο για προβολή, αλλά ενισχύει την ακρίβεια των συστάσεων με τον εξής τρόπο: 
\begin{enumerate} 
    \item \textbf{Επανατροφοδότηση Θεματικών Τίτλων στον Recommender (Semantic Boosting):} 
    Μια από τις πιο σημαντικές καινοτομίες στην αρχιτεκτονική του συστήματος είναι η χρήση της πληροφορίας των συστάδων ως "τροφή" για τον αλγόριθμο ομοιότητας. Η ετικέτα της συστάδας (\textit{cluster label}) που προέκυψε από το μοντέλο LDA δεν χρησιμοποιήθηκε απλώς ως μεταδεδομένο, αλλά επανεντάχθηκε στο κείμενο προς επεξεργασία.
    
    \item \textbf{Feature Boosting:} Στο στάδιο της προετοιμασίας του κειμένου (Preprocessing), η ετικέτα της συστάδας (\texttt{cluster\_label}) προστίθεται επαναλαμβανόμενες φορές στο πεδίο \texttt{text\_content}. Η επανάληψη αυτή είναι σκόπιμη, καθώς αυξάνει τεχνητά τη συχνότητα εμφάνισης του όρου (\textit{Term Frequency - TF}), δίνοντάς του μεγαλύτερο βάρος στο τελικό διάνυσμα TF-IDF.

    \textbf{Αποτέλεσμα στις Συστάσεις:}
    Με αυτή την τεχνική, επιτυγχάνεται η «σημασιολογική ενίσχυση» των συστάσεων. Ακόμα και αν δύο μαθήματα έχουν περιγραφές με εντελώς διαφορετικό λεξιλόγιο, η κοινή τους υπαγωγή στο ίδιο θεματικό cluster λειτουργεί ως "συνδετικός κρίκος". Αυτό αναγκάζει τα διανύσματά τους να συγκλίνουν στον πολυδιάστατο χώρο, διασφαλίζοντας ότι ο Recommender θα προτείνει μαθήματα που είναι θεματικά συγγενή, μειώνοντας τις πιθανότητες εμφάνισης άσχετων προτάσεων λόγω τυχαίας σύμπτωσης λέξεων.
\end{enumerate}

\subsection{Προσωποποιημένες Προτάσεις Χρηστών με χρήση ALS}
Τέλος, ένα ακόμη Spark Job που υλοποιήθηκε είναι εκείνο της πρότασης νέων μαθημάτων σε χρήστες, βάσει των μαθημάτων που έχουν 'σημαδέψει' ως αγαπημένα (Favorites). Οι προτάσεις γίνεται μέσω του ALS (Alternating Least Squares), μιας μεθόδου που ανήκει στην οικογένεια των Collaborative Filtering αλγορίθμων. 

\subsubsection{Γενική Περιγραφή ALS}
Η μέθοδος ALS στην ουσία βασίζεται στην παραγοντοποίηση ενός μεγάλου και αραιού μητρώου R (user-item interactions) στο γινόμενο 2 μητρώων:

\begin{itemize}
    \item $U$: 'Latent' Προτιμήσεις Χρηστών
    \item $V^T$: 'Latent' Χαρακτηριστικά Items
\end{itemize}

Αυτό που την διαφοροποιεί από άλλες μεθόδους είναι η εναλλαγή που κάνει ως προς την επίλυση μέσω Ελάχιστων Τετραγώνων (εξού και Alternating Least Squares). Σε κάθε επανάληψη 'φιξάρουμε' ένα από τα 2 μητρώα (U και V) και λύνουμε ως προς το άλλο, φροντίζοντας να μην λύσουμε ποτέ προς το ίδιο μητρώο σε 2 συνεχόμενες επαναλήψεις. Μετά από κάποιον αριθμό επαναλήψεων και όταν η συνάρτηση κόστους επιστρέψει ικανοποιητικά αποτελέσματα, έχουμε δύο μητρώα U' και V', όπου πολλαπλασιάζοντάς τα προκύπτει το νέο μητρώο R' το οποίο είναι πλέον πυκνό. Για κάθε χρήστη και κάθε item (κελί u,i) παράγεται ένα confidence score που υποδεικνύει το πόσο κοντά είναι το αντικείμενο αυτό στις προτιμήσεις του χρήστη.

\subsubsection{Εφαρμογή και υλοποίηση στην πρόταση μαθημάτων}
Στην δική μας περίπτωση, θέλουμε να προτείνουμε στον κάθε χρήστη ένα σύνολο μαθημάτων που θα μπορούσε να επιλέξει, βάσει των αγαπημένων του. Αξιοσημείωτο είναι το γεγονός πως τα μαθήματα δεν έχουν ratings (π.χ. 2/5, όπως οι ταινίες) αλλά μια binary συμβολοποίηση, εκείνη που είτε σε κάποιον χρήστη αρέσει (1) ή όχι (0) ένα μάθημα. Τα βήματα της υλοποίησης μας είναι τα εξής:

\begin{enumerate}
    \item Παίνρουμε τα δεδομένα από την βάση μας και τα τοποθετούμε σε ένα DataFrame.
    \item Αφού σημαδεύουμε κάθε course με 0 ή 1 για κάθε χρήστη, μετατρέπουμε τα IDs των χρηστών και των μαθημάτων από Strings σε Integers, για να εφαρμόσουμε ALS.
    \item Εφαρμόζουμε ALS στο μοντέλο μας και κρατάμε τις 10 καλύτερες προτάσεις για κάθε χρήστη.
    \item Μαζεύουμε τα IDs μαθημάτων του κάθε χρήστη και κάνουμε την αντίστροφη διαδικασία της προηγούμενης μετατροπής (Integer IDs -> String IDs). 
    \item Κάνουμε export τα αποτελέσματα σε έναν νέο πίνακα στην βάση δεδομένων μας, με όνομα user\_recommendations.
\end{enumerate}

Ο admin μπορεί να εκτελέσει το spark job στο admin panel και οι προτάσεις εμφανίζονται μαζί με τα αγαπημένα μαθήματα στον κάθε χρήστη.

Κατά την ανάπτυξη και την υλοποίηση του συστήματος προέκυψαν σημαντικά τεχνικά εμπόδια που αφορούσαν το περιβάλλον εκτέλεσης, τη διαχείριση των δεδομένων και τη συμβατότητα των βιβλιοθηκών του Spark.

\subsubsection{Μετάβαση από Windows σε WSL} 
Αρχικά, η εκτέλεση του Spark σε περιβάλλον Windows παρουσίασε κρίσιμα σφάλματα επικοινωνίας μεταξύ του Driver και των Executors, τα sockets εκρηγνύονταν με λίγα λόγια (\texttt{SocketTimeout} και \texttt{WinError 10038}). 

\begin{itemize} 
    \item \textbf{Πρόβλημα:} Η έκδοση της Python από το Windows Store και οι περιορισμοί του δικτύου των Windows εμπόδιζαν τη σωστή λειτουργία των \textit{worker processes} του Spark. 
    
    \item \textbf{Λύση:} Το σύστημα μεταφέρθηκε σε περιβάλλον \textbf{WSL (Ubuntu)}, το οποίο προσφέρει πλήρη συμβατότητα με τα POSIX συστήματα που απαιτεί το Spark. Έγινε χρήση εικονικού περιβάλλοντος (\texttt{venv}) και ορίστηκαν ρητά οι μεταβλητές περιβάλλοντος \texttt{PYSPARK\_PYTHON} και \texttt{PYSPARK\_DRIVER\_PYTHON} για τη διασφάλιση της ομοιομορφίας των εκδόσεων Python. 
\end{itemize}

\subsubsection{Διαχείριση Αναγνωριστικών MongoDB (\texttt{\_id})}
Η ενσωμάτωση του Spark με τη MongoDB (μέσω του MongoDB Spark Connector) παρουσίασε ιδιαιτερότητες στη διαχείριση του πεδίου \texttt{_id}. 

\begin{itemize} 
    \item \textbf{Πρόβλημα:} Το Spark αναπαριστά το \texttt{ObjectId} της MongoDB ως σύνθετο \texttt{StructType} (\texttt{{oid: string}}), γεγονός που καθιστούσε αδύνατη τη χρήση του ως κλειδί για συσχετίσεις (\textit{joins}) ή την επανεγγραφή του στη βάση. 
    
    \item \textbf{Λύση:} Κατά την ανάγνωση των δεδομένων, έγινε χρήση εναλλακτικών μοναδικών αναγνωριστικών (όπως το \texttt{externalId} το οποίο αναφέρεται απλά ως \texttt{course\_id}), διασφαλίζοντας ότι οι συστάσεις αποθηκεύονται με τρόπο που επιτρέπει την εύκολη ανάκτησή τους από τo Backend. 
\end{itemize}

\subsubsection{Ασυμβατότητα Βιβλιοθηκών \texttt{pyspark.ml} και \texttt{pyspark.mllib}} 

Ένα από τα πιο σύνθετα προβλήματα προέκυψε κατά την υλοποίηση του Σεναρίου 0 (Exact Similarity). 
\begin{itemize} 
    \item \textbf{Πρόβλημα:} Η σύγχρονη βιβλιοθήκη \texttt{pyspark.ml} (DataFrames) παράγει διανύσματα τύπου \texttt{SparseVector} που δεν είναι άμεσα συμβατά με τη χαμηλού επιπέδου βιβλιοθήκη \texttt{pyspark.mllib}, η οποία απαιτείται για τη δημιουργία του \texttt{IndexedRowMatrix} και την εκτέλεση κατανεμημένου πολλαπλασιασμού πινάκων. 
    
    \item \textbf{Λύση:} Υλοποιήθηκε ένας μηχανισμός μετατροπής των διανυσμάτων μέσα στο RDD pipeline, χρησιμοποιώντας τη μέθοδο \texttt{Vectors.fromML()}. Αυτό επέτρεψε τη ροή των δεδομένων από το NLP pipeline (DataFrames) στον κινητήρα γραμμικής άλγεβρας (RDD Matrices). 
\end{itemize}

\begin{minted}[frame=lines, fontsize=\footnotesize]{python}
# Η λύση στο πρόβλημα συμβατότητας των διανυσμάτων
from pyspark.mllib.linalg import Vectors as OldVectors
rdd_vectors = df.rdd.map(lambda row: IndexedRow(row.id,
                            OldVectors.fromML(row.features)))

\subsection{Σχεδιαστικές Αποφάσεις και Μελλοντική Επεκτασιμότητα}

\begin{itemize} 
    \item \textbf{Αρχικός Σχεδιασμός (Static Batch Processing):} Αρχικά έγινε η υπόθεση ότι η εφαρμογή θα λειτουργούσε στατικά. Σύμφωνα με αυτό το σενάριο, θα γινόταν \textit{harvest} ένα προκαθορισμένο σύνολο δεδομένων από APIs, θα εκτελούνταν εφάπαξ τα Spark Jobs (\texttt{clusterer.py} και \texttt{recommender.py}) και η εφαρμογή θα κατέληγε σε ένα παραδοσιακό Web App που ανακτά έτοιμα αποτελέσματα από τη MongoDB.

    \item \textbf{Προβλήματα Κλιμακωσιμότητας (Scalability Bottlenecks):} 
    Μετά από ανάλυση των πραγματικών συνθηκών, καταλήξαμε ότι ένα τέτοιο σύστημα θα δεχόταν νέο περιέχομενο με εξαιρετικά υψηλό ρυθμό. Η ανάγκη για επανεκτέλεση ολόκληρου του Spark Job (Batch) κάθε φορά που προστίθεται ένα μάθημα είναι υπολογιστικά ασύμφορη, ειδικά σε μη αποκεντρωμένα συστήματα. Σε περιβάλλοντα παραγωγής, η αναμονή για την ολοκλήρωση ενός Batch Job για την παραγωγή μιας σύστασης θα καθιστούσε το σύστημα μη αποκρίσιμο.

    \item \textbf{Μετάβαση σε Αρχιτεκτονική Kappa και χρήση Kafka:} 
    Για την αντιμετώπιση αυτού του προβλήματος, η ιδανική εξέλιξη του συστήματος βασίζεται στην \textbf{Αρχιτεκτονική Kappa (Kappa Architecture)}. Σε αυτή την προσέγγιση:
    \begin{itemize}
        \item Το \textbf{Apache Kafka} λειτουργεί ως ο κεντρικός δίαυλος (\textit{Unified Log}), όπου κάθε νέο μάθημα εισέρχεται ως ένα συμβάν (event) σε πραγματικό χρόνο.
        \item Το Spark δεν επεξεργάζεται πλέον όλη τη βάση από την αρχή, αλλά χρησιμοποιεί το \textbf{Spark Structured Streaming} για να επεξεργάζεται σταδιακά (\textit{incrementally}) τις νέες εγγραφές.
        \item Αντί για επανυπολογισμό ολόκληρου του πίνακα ομοιότητας, το σύστημα εκτελεί \textit{Online Scoring} ή χρησιμοποιεί προσεγγιστικούς αλγορίθμους (όπως το LSH που υλοποιήθηκε) για να εντάξει το νέο μάθημα στα υπάρχοντα clusters ακαριαία.
    \end{itemize}
\end{itemize}

    \subsection{Τελική Προσέγγιση: Triggered Batch Architecture (Admin-Driven)}

Στην τελική υλοποίηση, το σύστημα ακολουθεί μια αρχιτεκτονική \textbf{Triggered Batch}. Αντί οι διαδικασίες συλλογής και επεξεργασίας να εκτελούνται αυτόματα ή αποκλειστικά σε προκαθορισμένα χρονικά διαστήματα, ο έλεγχος δίνεται στον διαχειριστή (\textit{Admin}) μέσω ενός ειδικού περιβάλλοντος διεπαφής (Dashboard).

\textbf{Λογική και Πλεονεκτήματα:}
\begin{itemize}
    \item \textbf{On-demand Harvesting:} Ο διαχειριστής έχει τη δυνατότητα να ενεργοποιεί τη συλλογή δεδομένων από τους \texttt{API Connectors} μόνο όταν είναι απαραίτητο (π.χ. όταν υπάρχουν νέες πηγές). Αυτό αποτρέπει την άσκοπη κατανάλωση πόρων και τον περιορισμό από τα \textit{rate limits} των εξωτερικών συστημάτων.
    
    \item \textbf{Ελεγχόμενη Εκτέλεση Spark Jobs:} Όπως φαίνεται στο UI της εφαρμογής, η εκτέλεση των αλγορίθμων (Exact TF-IDF, Fast LSH, LDA, Hybrid) γίνεται κατ' επιλογή. Αυτό είναι ιδιαίτερα κρίσιμο σε περιβάλλοντα Big Data, καθώς επιτρέπει στον διαχειριστή να εκτελεί το βαρύ υπολογιστικό κομμάτι σε ώρες χαμηλού φόρτου συστήματος.
    
    \item \textbf{Διαχωρισμός Επιπέδων (Decoupling):} Η αρχιτεκτονική αυτή διαχωρίζει πλήρως το επίπεδο συλλογής (\textit{Data Ingestion}) από το επίπεδο επεξεργασίας (\textit{Spark Engine}). Ο διαχειριστής μπορεί να ολοκληρώσει το harvesting από πολλαπλές πηγές (π.χ. \texttt{api-1}, \texttt{api-2}) και στη συνέχεια να αποφασίσει ποιο συγκεκριμένο μοντέλο σύστασης θα «εκπαιδεύσει» πάνω στα νέα δεδομένα.
\end{itemize}

\textbf{Σύνδεση με Μελλοντική Επεκτασιμότητα:}
Η συγκεκριμένη «χειροκίνητη» προσέγγιση (\textit{Human-in-the-loop}) αποτελεί το απαραίτητο ενδιάμεσο στάδιο προς τον πλήρη αυτοματισμό. Η δομή του κώδικα είναι σχεδιασμένη ώστε τα Spark Jobs να μπορούν να μετατραπούν σε προγραμματισμένες εργασίες (\textit{Scheduled Tasks}) ή σε \textit{Streaming Consumers} (μέσω Apache Kafka) με ελάχιστες τροποποιήσεις, καθώς η λογική της επεξεργασίας παραμένει modular και ανεξάρτητη από τον τρόπο ενεργοποίησης.

\end{itemize}
